# 培训系统提示词 v1.1 条件路由修改方案

  ## 一、结论与文档改动总结

  你的思路可行，而且比“把现有提示词全部直接升级为 v1.1”更稳妥。最终规则确定为：

  文档涉及的实际修改面包括：

  1. 课程创建入口增加必选的课程类型，不再让模型自动猜测。
  2. 普通、互动、任务引擎三套大纲链路接收课程类型和 v1.1 策略。
  3. 管理/销售课程的大纲采用“开始引导—核心讲解—结尾应用”三层结构。
  4. slide-content 根据课程类型切换专业角色和内容约束。
  5. slide-actions 增加案例、痛点呼应、重点篇幅分配、实践技能导向等规则。
  6. quiz-content、quiz-actions 区分随堂检查与结尾综合复习。
  7. 新版课程时长改为：未指定时 15–40 分钟；用户明确要求时最多扩展到 50 分钟；普通场景允许 1–5 分钟。
  8. 管理/销售课程仅在用户开启现有联网开关且检索成功时使用联网资料；关闭、未配置或失败时继续生成，但不得伪造来源。
  9. “测验不通过不能继续”“多次作答记录最佳成绩”属于播放器、进度和成绩系统，不是提示词能够实现的功能，本阶段不纳入。

  ## 二、文档中需要校正的地方

  在把 docs/培训系统提示词文档（v1.1+修改版）.docx 落到代码前，应同步修正以下表述，避免实现时产生歧义：

  - 将“四大受众类型”改为“四类培训课程”。管理、销售、专业知识、公司制度描述的是课程领域，不完全等同于受众。
  - 增加第五个兜底类型“其他”，并明确其严格使用原版提示词。
  - 删除“模型自动识别并路由”的主方案，改为“用户在入口明确选择，服务端校验”。模型只根据已选择类型生成内容，不负责决定自
    己使用哪套提示词。

  - 明确现有“课程分类 categoryId”与新课程类型是两个字段：
      - 课程分类用于管理员保存、展示和管理课程；
      - 课程类型用于提示词路由；
      - 不按动态分类名称推断提示词版本。

  - 统一默认时长，删除 System Prompt 15–40 与 User Prompt 15–50 两个冲突默认值。改为“默认 15–40，用户明确要求时允许到
    50”。

  - 将“每分钟 1–2 个场景”的旧规则从 v1.1 分支移除，改为每个普通场景 60–300 秒，并让总场景时长落在课程目标时长内。
  - PBL 保留现有较长场景规则；任务引擎保留既有 10–14 场景、直接进入实操等硬约束，不套管理/销售三层结构。
  - “专业/制度尽量引用用户资料”不能只写在 Slide Prompt 中，因为当前 Slide 内容阶段拿不到完整 PDF 原文。需要在大纲阶段
    提取可核验的来源锚点并向后传递。

  - “全部场景提示词都修改 1–5 分钟”应改成“在大纲的 estimatedDuration 和总场景规划中统一控制”。当前 simulation、
    diagram、code、game、PBL 等内容模板并没有独立课程时长参数，不能机械替换不存在的值。

  - 将“随堂测试不通过才能继续”“课后测试记录最佳成绩”标记为后续运行时阶段。本阶段只能决定题目类型、放置位置和引导语言。
  - 文档当前写着“已应用全部修改”，但仓库代码仍是原提示词，应改成“待实施方案”或实施后再更新状态。
  - 调整实施顺序：课程类型字段和全链路传递必须先于 slide-content、slide-actions 修改，否则后两者没有可靠的路由依据。

  ## 三、实现设计

  ### 1. 建立独立、明确的课程类型契约

  在 lib/types/generation.ts 增加：

  type TrainingModule =
    | 'management'
    | 'sales'
    | 'professional'
    | 'company_policy'
    | 'other';

  并扩展以下公共数据：

  - UserRequirements.trainingModule?: TrainingModule
  - Stage.trainingModule?: TrainingModule
  - GenerateClassroomInput.trainingModule?: TrainingModule
  - 普通浏览器入口必须选择后才能生成。
  - API 为兼容旧调用方，缺失时按 other 处理；传入未知值时返回 400，不能由模型猜测。
  - categoryId 继续独立存在，不参与提示词路由。

  新增统一的服务端策略解析器，例如：

  interface CoursePromptPolicy {
    variant: 'legacy' | 'training-v1.1';
    trainingModule: TrainingModule;
    role:
      | 'management-master'
      | 'sales-expert'
      | 'professional-educator'
      | 'policy-educator'
      | 'legacy';
    useDeepStructure: boolean;
    sourceGrounded: boolean;
    defaultDurationRange?: [15, 40];
    explicitDurationMax?: 50;
  }

  所有生成路径都调用同一个解析器，禁止各路由分别根据中文名称、需求关键词或分类名称自行判断。

  ### 2. 课程入口与状态贯穿

  在首页需求输入区增加“课程类型”必选项，默认留空：

  - 管理知识培训
  - 销售培训
  - 专业知识培训
  - 公司制度培训
  - 其他课程（使用原版提示词）

  该字段应贯穿：

  1. 首页表单与 generationSession
  2. 大纲 SSE 请求
  3. 首场景内容与动作请求
  4. generationParams
  5. 课堂中剩余场景生成、失败重试和页面恢复
  6. Stage/IndexedDB 保存与重新加载
  7. 企业课程草稿中的 Stage 数据
  8. /api/generate-classroom 异步生成链路
  9. 编辑器后续重新生成 Slide 或讲稿的上下文

  这样可避免当前“需求只传到首个场景，后续场景和动作阶段丢失课程类型”的问题。该字段属于非索引 Stage 元数据，预计不需要
  新增 SQL 表或关系型数据库迁移，但需要补齐 Stage、IndexedDB 和企业课程 JSON 的序列化/反序列化。

  ### 3. 保留原版模板，按策略叠加 v1.1

  不复制整套大型提示词，也不直接把现有模板永久改成新版。在 lib/prompts 增加课程策略组合层：

  - 原有 buildPrompt(promptId, variables) 保持不变。
  - 新增 buildCoursePrompt(promptId, variables, policy)。
  - policy.variant === 'legacy' 时直接调用原有 buildPrompt，保证“其他课程”继续得到当前模板。
  - policy.variant === 'training-v1.1' 时，在原版模板上组合经过版本管理的 v1.1 System/User 规则片段。
  - v1.1 规则明确声明其角色、时长和结构要求覆盖基础模板中的通用默认值。
  - 不为每一种课程复制一份约 900 行的 slide-content，避免模板分叉后长期漂移。

  建议按行为拆分 v1.1 规则片段：

  - outline-structure
  - slide-role-and-grounding
  - quiz-purpose
  - slide-narration
  - quiz-narration
  - duration-policy

  ### 4. 大纲阶段的四类分支

  普通模式和互动模式：

  - 管理/销售：
      - Opening：主题概览、实践痛点、与相关理论的关系。
      - Opening 只提出核心问题，不提前给出最终答案。
      - Core：每个核心理论块回应 Opening 中的问题，并在主要知识块后安排 checkpoint Quiz。
      - Closing：系统回顾、回答 Opening 问题、工作应用步骤、工具或检查清单、综合复习。

  - 专业知识：
      - 保持标准大纲结构。
      - 优先使用用户需求、PDF和已提供资料中的专业事实。
      - 不允许为了丰富内容而编造技术参数、产品能力、标准编号或结论。

  - 公司制度：
      - 保持标准大纲结构。
      - 将制度原文、解释、示例明确区分。
      - 不允许凭常识补造公司的处罚、审批、福利、权限或合规条款。

  - 其他：
      - 不注入任何 v1.1 结构、角色、时长或 Quiz 规则。

  任务引擎模式继续拥有最高结构优先级：

  - 仍按当前任务引擎规则生成职业实操结构。
  - 不为管理/销售强制插入三层理论课程。
  - 课程类型只影响角色表达、来源约束、讲稿风格和新版时长上限。
  - 当前模式优先级保持 任务引擎 > 互动模式 > 普通模式。

  ### 5. 来源锚点，解决专业/制度资料无法传到内容阶段的问题

  扩展 SceneOutline：

  interface SourceAnchor {
    kind: 'requirement' | 'document' | 'research';
    text: string;
    label?: string;
  }

  sourceAnchors?: SourceAnchor[];
  courseSection?: 'opening' | 'core' | 'closing';

  quizConfig?: {
    // 现有字段保持
    purpose?: 'checkpoint' | 'final_review';
  };

  规则：

  - 每个场景最多保留 3 条短来源锚点，每条最多约 500 字符。
  - document 和 requirement 锚点必须能在规范化后的原始输入中找到；research 锚点必须来自实际 researchContext。
  - 校验失败的锚点直接丢弃，不能把模型自称的“来源”传给下游。
  - Slide、Quiz 和讲稿生成只接收当前场景的短锚点，不为每个场景重复发送完整 50,000 字 PDF 文本。
  - 公司制度课程有资料时，Slide 和讲稿优先引用锚点；没有资料时只能围绕用户明确输入生成通用培训框架，并明确不得虚构公司
    规则。

  - 管理/销售只有在现有联网开关开启且检索成功时才会出现 research 锚点；否则提示词明确要求不得伪造报告、出处或案例来
    源。

  ### 6. 内容与讲稿提示词

  slide-content：

  - 管理：将基础教育设计师角色专门化为“管理学大师”，强调理论框架、企业情境和系统解决思路。
  - 销售：专门化为“销售培训专家”，强调 ToC/ToB 场景、客户异议、销售动作和可落地方法。
  - 专业：保持教育内容设计能力，但专业事实必须以来源锚点为准。
  - 制度：保持教育内容设计能力，但必须区分制度原文、解释和示例。
  - 其他：继续使用当前 educational content designer 原版提示词。

  slide-actions：

  - 管理/销售：结合案例，回应 Opening 痛点和问题；重点内容增加讲解篇幅，次要内容简洁带过。
  - 专业：讲稿围绕专业事实、操作边界和风险提示，不将推测说成事实。
  - 制度：制度原文不得被讲稿改写成不同义务；解释和案例必须明确标识。
  - 所有四类新版都要求讲解引人入胜、节奏自然、目标指向实际工作能力。
  - “按重要性分配时长”通过讲稿篇幅和段落数量表达，不向动作 JSON 添加时间戳或 duration 字段，保持现有解析协议。

  quiz-content / quiz-actions：

  - checkpoint：检查刚完成的核心知识块，题目与前一组关键点直接对应，讲稿以快速检查和解释为主。
  - final_review：覆盖概念理解、应用判断和场景分析，作为课程结尾的综合复习。
  - 仅改变题目和引导语，不阻止用户切换场景。
  - 现有企业课后测评系统保持独立且不在本阶段修改；文档中的“强制通过、多次作答、最佳成绩”另立运行时阶段。

  ### 7. 时长规则

  四类 v1.1 课程：

  - 用户未指定时长：目标总时长 15–40 分钟。
  - 用户明确指定时长：遵从合理值，最高支持到 50 分钟。
  - 普通 Slide、Quiz、Interactive 场景：estimatedDuration 为 60–300 秒。
  - 场景数量根据内容块和总时长推导，不再使用“每分钟 1–2 个场景”。
  - PBL 继续使用其现有较长场景约束。
  - 任务引擎的场景数量和实操结构优先于通用时长推导。

  “其他”课程继续保留当前原版的 1–3 分钟、15–20/15–30 分钟等提示词行为，不受 v1.1 时长影响。

  ## 四、测试与验收

  ### 单元测试

  - 五种 TrainingModule 正确映射到 Prompt Policy。
  - 缺失类型的兼容 API 请求映射为 other；未知枚举返回 400。
  - other 渲染结果不包含管理大师、销售专家、三层结构、来源锚点或 v1.1 时长规则。
  - 管理/销售分别出现正确角色和三层结构，且不会串用对方角色。
  - 专业/制度使用标准结构，不出现管理/销售三层规则。
  - 制度提示词包含“不得编造公司制度”和“原文/解释/示例分离”规则。
  - 联网关闭、未配置或失败时，最终 Prompt 不声称已经取得联网资料。
  - checkpoint 与 final_review 正确进入 Quiz 内容和动作提示词。
  - 来源锚点只接受能够在真实输入中核验的内容，并满足数量、长度限制。
  - 任务引擎与管理/销售组合时，任务引擎结构规则优先。
  - v1.1 时长与 legacy 时长分别渲染，不同时出现冲突默认值。

  ### 链路测试

  - 首页未选择课程类型时不可生成，并给出明确提示。
  - 课程类型与管理员课程分类可以独立选择、独立保存。
  - SSE 大纲、首场景、后续场景、失败重试和恢复生成均携带同一课程类型。
  - /api/generate-classroom 显式传入四类时使用 v1.1；旧调用方未传时保持原版。
  - Stage 保存、重新打开、企业课程草稿同步后仍保留课程类型。

  ### 验收标准

  - 选择“其他”生成的课程与修改前保持原版提示词行为。
  - 四类课程只在用户明确选择后进入 v1.1，不进行静默关键词猜测。
  - 管理与销售课程的大纲能够看到 Opening/Core/Closing 结构和前后问题呼应。
  - 专业与制度课程能够把真实资料锚点传到 Slide 和讲稿阶段。
  - 关闭联网仍可生成，且不出现虚构的“根据某报告/某权威来源”。
  - 任务引擎现有职业实操结构不被三层理论结构破坏。
  - 本阶段不出现“测验未通过禁止下一页”等新的播放器行为。

  ## 五、实施边界与默认约定

  - 本方案只规划提示词路由、提示词内容、必要的类型和上下文传递，不实现测验门禁、最佳成绩或新的学习进度规则。
  - 不复用动态课程分类名称做提示词判定。
  - 不让模型自动决定是否走 v1.1。
  - 不修改 TTS 逻辑；TTS 继续朗读新版动作提示词生成的讲稿。
  - 不机械修改文档列出的全部场景模板；时长在大纲规划这一真实来源处控制。
  - 当前 DOCX 是工作区未跟踪文件，实施时保留它，不把它与无关改动一起处理。
  - 当前阶段仅完成了只读分析，没有修改仓库文件。
