## 一、实施目标

本计划负责课程生成核心链路，目标不是简单地在旧 Prompt 末尾追加几段规则，而是建立可版本化、可恢复、可验证的课程生成策略机制：

1. 用户明确选择课程类型，服务端统一解析提示词策略；
2. 管理、销售、专业知识、公司制度进入 `training-v1.1`，其他课程严格保持 `legacy`；
3. 课程类型与提示词策略版本贯穿大纲、内容、讲稿、失败重试、页面恢复、编辑器重生成、异步生成和持久化；
4. 用 `teachingBrief` 保存每个场景必须讲解的内容，用 `sourceRefs` 保存可信来源引用，避免一个字段同时承担内容规划和来源证明；
5. 来源先由服务端分块并编号，模型只能选择已有引用 ID；
6. 通过结构化校验和输出覆盖检查，减少用户详细输入在“大纲 → 内容 → 讲稿”过程中被压缩或遗漏；
7. 保留任务引擎、互动模式、PBL、企业课程草稿、IndexedDB 和课程 ZIP 的既有兼容行为。

## 二、当前代码基线与主要缺口

### 2.1 已确认的当前链路

当前普通浏览器生成链路是：

```text
app/page.tsx
  → sessionStorage.generationSession
  → app/generation-preview/page.tsx
  → /api/generate/scene-outlines-stream
  → /api/generate/scene-content（首场景）
  → /api/generate/scene-actions（首场景）
  → sessionStorage.generationParams
  → app/classroom/[id]/page.tsx
  → lib/hooks/use-scene-generator.ts（后续场景）
```

另有独立的服务端生成链路：

```text
/api/generate-classroom
  → classroom job
  → lib/server/classroom-generation.ts
  → 非 SSE 大纲生成
  → 所有场景内容、actions、媒体和 TTS
```

### 2.2 当前缺口

- `UserRequirements` 没有课程类型和提示词策略版本；
- 首页 `FormState` 和 `canGenerate` 只校验需求、模型及管理员课程分类；
- `Stage`、`StageRecord`、`StageListItem` 只保存 `interactiveMode`、`taskEngineMode` 等现有标记；
- 首场景 `scene-content` 会收到 `requirements`，但 `scene-actions` 没有统一课程上下文；
- `generationParams` 没有保存完整 `requirements` 或提示词策略，课堂续生成时 `fetchSceneContent()` 也没有继续传入；
- 编辑器 Agent 的 `regenerate_scene`、`regenerate_scene_actions` 只取得场景、内容和语言等上下文，旧课程策略不能稳定复用；
- `/api/generate-classroom` 只有普通生成输入，没有课程类型/策略版本，也不等价于浏览器端的互动或任务引擎路由；
- Prompt 调用仍直接使用 `buildPrompt()`，旧角色、旧时长、旧 Quiz 规则分散在多个模板中；
- 大纲结果只有 `description`、`keyPoints` 等字段，没有“必须覆盖项”和可信来源引用；
- PDF 兼容返回值主要是合并文本，部分解析器有页码布局信息，但不能假设所有解析器都能提供逐页文本；
- 前端联网检索当前只持久化简化后的标题和 URL，且浏览器检索失败会中断生成，不符合 v1.1 的“失败后降级继续生成”；
- 课程 ZIP v1 不保存提示词策略、大纲和来源上下文，导入后无法可靠按 v1.1 重生成。

## 三、范围与非目标

### 3.1 本计划范围

- 课程类型、策略版本、统一生成上下文和运行时校验；
- 多维 `CoursePromptPolicy`；
- 来源注册表、场景教学任务书、来源引用与解析边界校验；
- 普通、互动、任务引擎大纲路由；
- Slide、Quiz、Interactive、PBL 内容与 actions 的策略消费；
- 浏览器首场景、课堂续生成、失败重试、恢复、编辑器重生成；
- `/api/generate-classroom` 的 v1.1 普通生成支持；
- Stage、IndexedDB、企业课程 JSON、课程 ZIP 的兼容和持久化；
- 单元、链路、兼容和 Prompt 合同测试。

### 3.2 明确不做

- 不实现“测验不通过禁止下一场景”；
- 不实现多次答题取最佳成绩；
- 不修改现有企业课后测评业务规则；
- 不修改 TTS 协议，TTS 继续朗读 actions 生成的讲稿；
- 不根据动态 `categoryId` 或分类中文名称推断课程类型；
- 不让模型决定自己使用 legacy 还是 v1.1；
- 不承诺 PDF 原版版式或逐字还原；
- 本阶段不把 `/api/generate-classroom` 扩展为与浏览器完全相同的互动/任务引擎编排，除非另行明确该 API 的输入合同和验收范围。

## 四、最终数据契约

### 4.1 课程类型和策略版本

在 `lib/types/generation.ts` 定义唯一枚举源。建议使用含义更准确的 `TrainingCourseType`，不继续使用容易被理解为“功能模块”的 `TrainingModule`：

```ts
export const TRAINING_COURSE_TYPES = [
  'management',
  'sales',
  'professional',
  'company_policy',
  'other',
] as const;

export type TrainingCourseType = (typeof TRAINING_COURSE_TYPES)[number];
export type PromptPolicyVersion = 'legacy' | 'training-v1.1';
export type ResearchStatus = 'disabled' | 'unconfigured' | 'failed' | 'succeeded';
```

扩展：

```ts
interface UserRequirements {
  // 现有字段保持
  trainingCourseType?: TrainingCourseType;
  promptPolicyVersion?: PromptPolicyVersion;
}

interface CourseGenerationContext {
  trainingCourseType: TrainingCourseType;
  promptPolicyVersion: PromptPolicyVersion;
  requirements: UserRequirements;
  researchStatus: ResearchStatus;
  sourceCatalog?: SourceCatalogEntry[];
}
```

服务端兼容规则固定为：

| 请求状态 | 服务端结果 |
| --- | --- |
| 新建管理/销售/专业/制度课程 | 固定解析为 `training-v1.1` |
| 新建其他课程 | 固定解析为 `legacy` |
| 老 API 调用完全缺少新字段 | 归一化为 `other + legacy` |
| 历史 Stage 缺少新字段 | 读取为 `other + legacy` |
| 未知课程类型或未知版本 | 返回 HTTP 400 |
| 类型与版本组合冲突 | 返回 HTTP 400，不静默猜测 |
| 编辑器重生成 | 使用 Stage 已保存版本，不使用当前系统最新版本覆盖 |

客户端不能提交完整 `CoursePromptPolicy`。客户端只提交课程类型及已有 Stage 的策略版本，具体策略始终由服务端解析。

### 4.2 多维提示词策略

新增 `lib/generation/course-prompt-policy.ts`：

```ts
interface CoursePromptPolicy {
  variant: PromptPolicyVersion;
  trainingCourseType: TrainingCourseType;
  role:
    | 'management-master'
    | 'sales-expert'
    | 'professional-educator'
    | 'policy-educator'
    | 'legacy';
  structure: 'legacy' | 'three-phase' | 'standard-training' | 'task-engine';
  grounding: 'open' | 'source-primary' | 'source-only';
  duration: 'legacy' | 'training-v1.1' | 'task-engine';
  quizStrategy: 'legacy' | 'checkpoint-and-final' | 'task-engine';
  allowResearch: boolean;
}
```

策略映射：

| 课程类型 | 角色 | 普通/互动结构 | 来源强度 | 联网 |
| --- | --- | --- | --- | --- |
| 管理 | `management-master` | `three-phase` | `open` | 仅真实成功时可引用 |
| 销售 | `sales-expert` | `three-phase` | `open` | 仅真实成功时可引用 |
| 专业知识 | `professional-educator` | `standard-training` | `source-primary` | 按现有开关 |
| 公司制度 | `policy-educator` | `standard-training` | `source-only` | 不用联网内容补造公司制度 |
| 其他 | `legacy` | `legacy` | `open` | 保持原版 |

模式优先级按维度计算：

- 任务引擎覆盖 `structure`、`duration` 和 `quizStrategy`；
- 课程类型仍决定 `role` 和 `grounding`；
- 互动模式仅决定可用场景类型和互动大纲模板，不取消课程来源约束；
- 公司制度即使进入任务引擎，也必须保持 `source-only`；
- 不用一个 `taskEngineMode` 布尔值把全部 v1.1 策略整体覆盖掉。

### 4.3 场景教学任务书与来源引用

扩展 `SceneOutline`：

```ts
interface SceneTeachingBrief {
  mustCover: string[];
  supportingDetails: string[];
  applicationFocus?: string[];
  userConstraints?: string[];
}

interface SourceRef {
  kind: 'requirement' | 'document' | 'research';
  sourceId: string;
  chunkId: string;
}

interface SceneOutline {
  // 现有字段保持
  teachingBrief?: SceneTeachingBrief;
  sourceRefs?: SourceRef[];
  courseSection?: 'opening' | 'core' | 'closing';
  quizConfig?: {
    // 现有字段保持
    purpose?: 'checkpoint' | 'final_review';
  };
}
```

职责必须保持分离：

- `teachingBrief.mustCover`：本场景必须进入可见内容或讲稿的结论、步骤、数字、限制条件；
- `supportingDetails`：用于解释但不一定全部展示在 Slide；
- `applicationFocus`：管理、销售或实操课程的工作应用目标；
- `userConstraints`：不得改写、不得补造、受众、语气等用户限制；
- `sourceRefs`：只证明内容依据，不承担教学规划。

## 五、可信来源注册表设计

### 5.1 来源结构

新增 `lib/generation/source-registry.ts`，服务端在大纲调用前建立注册表：

```ts
interface SourceChunk {
  id: string;
  kind: 'requirement' | 'document' | 'research';
  sourceId: string;
  text: string;
  label?: string;
  pageNumber?: number;
  url?: string;
  contentHash: string;
}

type SourceCatalogEntry = SourceChunk;
```

编号建议：

```text
REQ-001
REQ-002
DOC-001-001
DOC-001-002
WEB-001-001
```

### 5.2 分块规则

- 用户需求按段落、列表项和明确约束分块，不能只按固定字符数盲切；
- PDF/文档优先使用带页码的布局块；解析器没有逐页文本时，按标题/段落分块，`pageNumber` 留空，不能伪造页码；
- 联网来源使用搜索结果的结构化标题、URL 和正文摘要，不再只依赖拼接后的 `researchContext`；
- 每块设置服务端长度上限，Prompt 中只传必要短块；
- 需求、文档和联网资料都包裹为“不可信参考资料”，明确禁止执行资料中的指令，降低文档型 Prompt Injection 风险；
- 全量注册表只在大纲生成和校验期间使用，持久化时只保留实际被引用的去重块，避免把完整 50,000 字 PDF 复制到每个场景；
- 不记录密钥、鉴权头或供应商原始响应。

### 5.3 模型输出与服务端校验

大纲 Prompt 只允许返回引用 ID：

```json
{
  "sourceRefs": ["REQ-002", "DOC-001-003"]
}
```

SSE 与非 SSE 大纲路径必须复用同一个 `normalizeAndValidateOutline()`：

1. 校验课程结构、枚举、数组长度和字段长度；
2. 检查 `sourceRefs` 是否存在于本次注册表；
3. 限制每场景引用数量并去重；
4. 丢弃未知、篡改或越权 ID；
5. 将被引用的条目加入精简 `sourceCatalog`；
6. 记录不含敏感正文的诊断信息；
7. 将规范化后的 outline 发送给客户端或异步生成器。

不能继续采用“让模型返回引用文本，再用字符串查找原文”的方案。

### 5.4 联网状态

`ResearchStatus` 必须进入生成上下文：

- `disabled`：用户未开启；
- `unconfigured`：用户开启但没有可用供应商；
- `failed`：调用失败或没有有效结果；
- `succeeded`：存在可校验的结构化来源块。

只有 `succeeded` 允许生成 research 引用。无 research 引用的管理/销售案例必须标记为“模拟案例”或“示例情境”，不得写成真实企业案例。

## 六、Prompt 组合重构

### 6.1 目标结构

在 `lib/prompts` 增加课程策略组合层，建议结构：

```text
lib/prompts/
  course/
    build-course-prompt.ts
    fragments/
      legacy/
      training-v1.1/
        role/
        structure/
        duration/
        grounding/
        quiz/
        narration/
```

对课程生成 Prompt 提供：

```ts
buildCoursePrompt(promptId, variables, courseContext)
```

### 6.2 组合原则

- `buildPrompt()` 继续服务非课程 Prompt；
- 所有课程生成调用点迁移到 `buildCoursePrompt()`；
- 从现有大模板中只抽出会随策略变化的角色、结构、时长、来源、Quiz 和讲稿规则；
- legacy 片段保留现有规则，v1.1 选择另一组唯一片段；
- 不复制完整 `slide-content` 等大型模板；
- 不采用“旧规则完整保留 + 末尾声明新版覆盖”的方式；
- 用测试保证 `other + legacy` 的渲染结果与改造前基线一致；
- 构建完成后不得出现未解析的 `{{coursePolicy}}`、`{{sourceRefs}}`、`{{teachingBrief}}` 等占位符。

### 6.3 v1.1 规则

#### 管理和销售大纲

- 普通/互动模式使用 Opening → Core → Closing；
- Opening 只提出实践痛点和核心问题，不提前给最终答案；
- Core 的主要知识块回应 Opening，并在合适位置安排 `checkpoint`；
- Closing 回答 Opening 问题，给出应用步骤、工具/清单和 `final_review`；
- 任务引擎保留职业实操结构，不强制套三层理论课。

#### 专业知识

- 标准培训结构；
- 用户需求和资料为优先依据；
- 可以补充通用专业知识，但不得编造技术参数、标准编号、产品能力或确定性结论；
- 事实性 `mustCover` 尽可能绑定有效来源。

#### 公司制度

- 标准培训结构；
- 审批、处罚、福利、权限、流程和合规要求只能来自 requirement/document 来源；
- 没有有效制度来源时，只允许生成培训框架、阅读引导和待补充项；
- 制度原文、解释和模拟示例必须明确区分。

#### 时长

- v1.1 未明确指定：总时长 15–40 分钟；
- 用户明确要求：合理遵从，最高 50 分钟；
- 普通 Slide、Quiz、Interactive：`estimatedDuration` 60–300 秒；
- 移除 v1.1 分支中的“每分钟 1–2 个场景”；
- PBL 保留现有较长场景约束；
- 任务引擎的 10–14 场景和实操结构优先；
- legacy 不注入上述新时长。

#### 内容和讲稿

- Slide、Quiz、Interactive、PBL 内容和 actions 都接收当前 `teachingBrief`、已解析短来源和 Policy；
- 讲稿按重要性通过篇幅与段落组织表达，不修改 actions JSON 协议增加时间戳；
- `checkpoint` 只检查刚完成的知识块；
- `final_review` 覆盖概念、应用判断和场景分析；
- 不加入播放器门禁。

### WP-08：覆盖校验

新增 `lib/generation/coverage-validator.ts`：

1. 收集 Slide 可见文本、Quiz 题干/解析和 actions 讲稿；

3. 将每个 `mustCover` 标记为 `covered`、`missing` 或 `uncertain`；
4. 硬约束缺失时允许一次有界修复，不做无限重试；
5. 仍缺失时暂停当前场景或记录明确诊断，不能静默宣称已覆盖；

## 十、发布、灰度与回滚

### 10.1 灰度

- 用服务端能力/功能开关控制 v1.1 是否对首页开放；
- 先在测试环境验证 legacy、四类 v1.1、互动、任务引擎和无来源制度课程；
- 开关关闭时，前端不展示未完成的课程类型入口，新 API 仍可读取历史字段；
- 不用仅前端环境变量作为唯一保护，服务端必须校验功能是否启用。

### 10.2 可观测性

只记录非敏感诊断：

- 策略版本和课程类型；
- `ResearchStatus`；
- 来源块数量、有效引用数量、被剔除引用数量；
- `mustCover` 数量和 `covered/missing/uncertain` 计数；
- Prompt ID、生成阶段和失败原因分类。

不得记录完整需求、完整 PDF、搜索正文、密钥或鉴权信息。

### 10.3 回滚

- 新课程入口开关可立即关闭；
- 已保存的 v1.1 课程继续携带版本，不改写为 legacy；
- 回滚代码必须能容忍未知可选 JSON 字段；
- 不删除 IndexedDB/企业 JSON 中的新字段；
- 不对历史课程批量升级或降级，迁移必须另立任务。

## 十一、完成定义

只有同时满足以下条件，核心生成链路才算完成：

- 课程类型由用户或显式 API 输入决定，模型不参与路由；
- legacy 渲染基线和历史课程行为通过测试；
- 四类 v1.1 课程从大纲到重生成始终保留相同策略版本；
- 管理/销售、专业/制度、互动/任务引擎的优先级符合策略矩阵；
- 来源只能引用服务端存在的 ID，联网失败不伪造来源；
- 详细输入通过 `teachingBrief` 进入内容和讲稿，而不只是出现在大纲 Prompt；
- Stage、IndexedDB、企业 JSON 和选定的 ZIP 策略均通过往返测试；
- 浏览器前端计划中的必选课程类型、资料不足提示和可追溯展示完成验收；
- 构建、相关测试、格式检查和浏览器验收均有可复核结果。
