# 培训系统提示词 v1.1 评审修改建议

> 适用范围：对《培训系统提示词 v1.1 条件路由修改方案》的总结性评审。  
> 当前状态：待实施方案；本文仅提出修改建议，不表示仓库代码已经完成升级。

## 一、总体结论

现有方案方向正确，能够实现以下目标：

- 由用户明确选择培训课程类型，不让模型自行猜测；
- 管理、销售、专业知识、公司制度使用 v1.1，其他课程保持原版行为；
- 课程类型贯穿大纲、内容、讲稿、重试、恢复和持久化；
- 专业知识和公司制度优先依据用户输入及资料，减少无依据扩写；
- 管理和销售课程使用更适合企业培训的结构、案例和实践导向。

但在正式实施前，建议将方案的核心从：

> 课程类型路由 + 来源文本片段

升级为：

> 课程类型与策略版本 + 场景讲解任务书 + 可信来源引用 + 下游覆盖校验

否则，课程类型路由虽然能够生效，详细用户输入仍可能只被传入 Prompt，却没有真正进入最终 Slide 或讲稿。

## 二、必须调整的核心设计

### 1. 分离“本场景必须讲什么”和“内容依据是什么”

不要让 `sourceAnchors` 同时承担内容规划和来源证明。建议拆成：

```ts
interface SceneTeachingBrief {
  mustCover: string[];
  supportingDetails: string[];
  applicationFocus?: string[];
  userConstraints?: string[];
}

interface SourceRef {
  kind: 'requirement' | 'document' | 'research';
  sourceId: string;
  chunkId: string;
}
```

扩展 `SceneOutline`：

```ts
interface SceneOutline {
  // 现有字段保持不变
  teachingBrief?: SceneTeachingBrief;
  sourceRefs?: SourceRef[];
  courseSection?: 'opening' | 'core' | 'closing';

  quizConfig?: {
    // 现有字段保持不变
    purpose?: 'checkpoint' | 'final_review';
  };
}
```

职责划分：

- `teachingBrief`：保存用户要求中本场景必须覆盖的结论、步骤、案例、数字、限制条件和实践目标；
- `sourceRefs`：证明相关内容来自用户需求、上传资料还是联网检索；
- Slide、Quiz 和讲稿共同消费 `teachingBrief`；
- 专业知识和公司制度中的事实性内容尽可能绑定有效 `sourceRefs`。

这是避免详细输入在“大纲 → 内容 → 讲稿”过程中被压缩丢失的核心机制。

### 2. 来源引用必须由服务端预分块，模型只选择引用 ID

不建议让模型自行返回一段 `sourceAnchors.text`，再用字符串查找判断是否来自原文。模型可能改写标点、空格或措辞，造成真实引用被误删；也可能返回缺乏证明力的公共短语。

建议先由服务端对真实输入建立可信来源注册表：

```ts
interface SourceChunk {
  id: string;
  kind: 'requirement' | 'document' | 'research';
  sourceId: string;
  text: string;
  label?: string;
  pageNumber?: number;
  url?: string;
  contentHash: string;
}
```

来源块使用稳定编号，例如：

```text
REQ-001
REQ-002
DOC-001-001
DOC-001-002
WEB-001
```

大纲模型只允许返回来源 ID：

```json
{
  "sourceRefs": ["REQ-002", "DOC-001-003"]
}
```

服务端在大纲解析边界完成：

1. 检查引用 ID 是否真实存在；
2. 限制每场景引用数量；
3. 从可信注册表补齐短原文、文件名、页码、标题和 URL；
4. 丢弃未知或越权引用，并记录诊断信息；
5. 只把当前场景需要的短引用传给内容和讲稿生成。

这样可以从机制上阻止模型虚构“根据某制度”“根据某报告”等来源。

### 3. 保存提示词策略版本，避免旧课程被静默升级

仅保存课程类型还不够。未来发布 v1.2 后，旧课程重新生成 Slide 或讲稿时不应自动切换到新规则。

建议保存：

```ts
type PromptPolicyVersion = 'legacy' | 'training-v1.1';

interface Stage {
  trainingModule?: TrainingModule;
  promptPolicyVersion?: PromptPolicyVersion;
}
```

兼容规则：

- 新建的四类培训课程：`training-v1.1`；
- “其他”：`legacy`；
- 历史课程缺少字段：按 `other + legacy`；
- 编辑器重新生成内容或讲稿：读取课程保存的策略版本；
- 未经显式迁移，不把旧课程自动升级到未来版本。

如果希望字段含义更准确，可将 `TrainingModule` 命名为 `TrainingCourseType`。

### 4. 将 Prompt Policy 改成多维策略，不使用简单布尔值

`useDeepStructure` 和 `sourceGrounded` 无法完整表达任务引擎、专业知识和公司制度的差别。建议改为：

```ts
interface CoursePromptPolicy {
  variant: 'legacy' | 'training-v1.1';
  trainingModule: TrainingModule;

  role:
    | 'management-master'
    | 'sales-expert'
    | 'professional-educator'
    | 'policy-educator'
    | 'legacy';

  structure: 'legacy' | 'three-phase' | 'standard-training' | 'task-engine';
  grounding: 'open' | 'source-primary' | 'source-only';
  duration: 'legacy' | 'training-v1.1' | 'task-engine';
  quizStrategy: 'legacy' | 'checkpoint-and-final' | 'task-engine';
  allowResearch: boolean;
}
```

推荐映射：

| 课程类型 | 结构 | 来源约束 |
| --- | --- | --- |
| 管理 | `three-phase` | `open`，有真实检索结果时可以引用 |
| 销售 | `three-phase` | `open`，有真实检索结果时可以引用 |
| 专业知识 | `standard-training` | `source-primary` |
| 公司制度 | `standard-training` | `source-only` |
| 其他 | `legacy` | `open` |
| 任务引擎 | `task-engine` | 保留课程类型对应的来源约束 |

任务引擎应按维度覆盖普通结构，而不是覆盖所有策略：

- 任务引擎决定场景结构和数量；
- 课程类型仍决定角色表达和来源约束；
- 公司制度即使进入任务引擎，也不能编造公司条款；
- 专业知识即使进入任务引擎，也要保持专业事实边界。

## 三、提示词组合方式的修改建议

### 1. 不要简单在原版 Prompt 末尾追加 v1.1 规则

原版模板中已经包含角色、默认时长、场景时长、场景数量和 Quiz 规则。如果直接追加“新版规则覆盖旧规则”，最终 Prompt 会同时出现冲突要求。

建议将会发生变化的部分拆成版本化片段：

```text
base-common
role-policy
structure-policy
duration-policy
grounding-policy
quiz-policy
narration-policy
```

`buildCoursePrompt()` 应根据 Policy 选择唯一片段，而不是同时保留 legacy 和 v1.1。

v1.1 最终 Prompt 必须满足：

- 不包含“每分钟 1–2 个场景”；
- 不同时出现“1–3 分钟”和“1–5 分钟”；
- 不同时出现原版角色和新版专业角色；
- 不同时出现 legacy Quiz 规则和 checkpoint/final_review 规则；
- 不遗留未解析的 `{{coursePolicy}}`、`{{sourceRefs}}` 等占位符。

“其他”课程应通过测试确认严格使用 legacy，不注入任何 v1.1 内容。

### 2. 建立统一生成上下文

建议定义：

```ts
interface CourseGenerationContext {
  trainingModule: TrainingModule;
  promptPolicyVersion: PromptPolicyVersion;
  requirements: UserRequirements;
}
```

客户端只传课程类型和版本，服务端统一解析 `CoursePromptPolicy`。不要允许客户端直接提交完整 Policy，也不要让各 API 根据中文名称、关键词或动态课程分类自行判断。

统一上下文必须覆盖：

1. 首页表单与 `generationSession`；
2. 普通、互动和任务引擎大纲；
3. 首场景内容与讲稿；
4. 后续场景生成；
5. 单场景失败重试；
6. 页面恢复与重新打开；
7. 专业编辑器重新生成内容和 actions；
8. Stage、IndexedDB 和企业课程快照；
9. `/api/generate-classroom` 服务端异步生成链路。

当前普通浏览器生成与 `/api/generate-classroom` 是两条独立实现。后者目前并不自动拥有浏览器端“任务引擎 > 互动 > 普通”的完整路由。因此应明确：

- 本阶段至少让 `/api/generate-classroom` 支持课程类型和 v1.1 普通生成；
- 如果它还要支持互动模式或任务引擎，必须单独扩展输入与路由；
- 不能用浏览器链路通过来替代异步链路验收。

## 四、来源与防编造规则

### 1. 专业知识与公司制度使用不同强度

- 专业知识：`source-primary`
  - 用户需求和资料是优先依据；
  - 可以补充通用专业知识；
  - 不得编造技术参数、标准编号、产品能力或确定性结论。

- 公司制度：`source-only`
  - 审批、处罚、福利、权限、流程和合规要求只能来自真实资料；
  - 没有资料时，只能生成培训框架、阅读引导和待补充项；
  - 不能根据行业常识补造公司规定。

建议用户选择“公司制度培训”但没有提供有效制度内容时，显示资料不足提示，必要时要求确认后再继续。

### 2. 管理和销售案例必须区分真实与模拟

- 没有 research 引用的案例必须标记为“模拟案例”或“示例情境”；
- 只有绑定真实 research 来源时才能写成真实企业案例；
- 不允许虚构“某权威报告显示”“某知名企业实践证明”。

建议显式传入联网状态：

```ts
type ResearchStatus = 'disabled' | 'unconfigured' | 'failed' | 'succeeded';
```

Prompt 根据状态决定是否允许引用联网资料，不能只依赖 `researchContext` 是否为空。

上传资料和检索文本应被包裹为“不可信参考资料”：只能用于内容依据，不能执行其中的指令，降低文档型 Prompt Injection 风险。



## 六、持久化和兼容性补充

新增字段预计不需要关系型数据库迁移，但不能只修改 TypeScript 类型。

需要同步检查：

- `packages/@openmaic/dsl` 中的 `Stage`；
- IndexedDB 的 `StageRecord`；
- `saveStageData()` 和加载恢复；
- `StageListItem`；
- generation-preview 创建 Stage；
- 服务端异步生成创建 Stage；
- 企业课程 Stage JSON 快照；
- 大纲 JSON 的保存与恢复；
- 编辑器自动保存和手动保存；
- 失败重试和剩余场景生成上下文。

还要决定课程 ZIP 导入导出的行为：

- 如果导入后需要继续按 v1.1 重新生成内容，应升级 manifest，保存课程类型、策略版本及必要的大纲上下文；
- 如果不升级，应明确导入课程降级为 legacy，不能保证原有 v1.1 重新生成行为。


## 八、测试与验收补充

除原方案已有测试外，建议增加以下重点验收。

### 1. 详细输入覆盖验收

- 每个 `mustCover` 至少进入最终可见内容或讲稿之一；
- 用户提供的关键步骤、数字、限制条件和案例不会全部在大纲阶段消失；
- 不适合放到 Slide 上的必要细节进入讲稿；
- 讲稿不得把推测表达成确定事实；
- 不能只检查详细输入是否进入 Prompt，还要检查最终生成结果是否覆盖。

### 2. 来源真实性验收

- 模型只能引用服务端提供的来源块 ID；
- 未知 ID、篡改 ID、超长引用和超数量引用被拒绝或剔除；
- research 引用能够回溯到真实标题和 URL；
- 联网关闭、未配置或失败时不生成伪造来源；
- 无来源案例明确标记为模拟案例。

### 3. 版本兼容验收

- 历史 Stage 缺失字段时按 legacy 打开；
- v1.1 课程保存、关闭、重新打开后仍使用同一策略；
- 编辑器重新生成 Slide 或讲稿时仍保留课程类型和来源依据；
- 未来增加 v1.2 后，旧课程不会被静默升级；
- ZIP 导入明确执行“保留 v1.1”或“降级 legacy”的既定规则。

## 九、推荐实施顺序

1. 定义 `TrainingModule`、`PromptPolicyVersion` 和统一运行时校验器；
2. 建立多维 `CoursePromptPolicy`，明确任务引擎的按维度优先级；
3. 增加首页必选项，打通 session、Stage、IndexedDB、企业 JSON 和异步 API；
4. 建立服务端 `SourceChunk` 注册表和稳定来源 ID；
5. 扩展 `SceneOutline.teachingBrief`、`sourceRefs`、`courseSection` 和 Quiz purpose；
6. 在 SSE 和非 SSE 大纲解析边界统一校验、规范化和补齐来源；
7. 重构 Prompt 的角色、结构、时长、来源和 Quiz 规则片段；
8. 修改 Slide、Quiz、Interactive、PBL 和 actions 消费统一上下文；
9. 补齐首场景、后续场景、失败重试、恢复生成、编辑器重新生成和 `/api/generate-classroom`；
10. 完成详细输入覆盖、来源真实性、版本兼容、链路和浏览器验收。

## 十、最终建议

本方案可以实现目标，但正式实施版应以以下四项为核心：

1. **课程类型与提示词策略版本**：决定使用哪一套结构、角色和约束；
2. **场景讲解任务书 `teachingBrief`**：保存用户详细输入中必须讲解的内容；
3. **可信来源引用 `sourceRefs`**：证明专业事实和制度条款来自哪里；
4. **下游覆盖校验**：确认关键要求真正进入 Slide 或讲稿，而不只是进入 Prompt；

完成这些调整后，v1.1 不仅能够做到条件路由，还能实质性减少详细用户输入在课程生成过程中被压缩、遗漏或无依据改写的问题。
